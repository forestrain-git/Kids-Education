# 物理提分助手 — 测试计划

## 1. 测试目标

1. **功能正确性**：核心学习流程（推荐 → 答题 → 反馈 → 记录）在各场景下数据计算准确
2. **数据持久化**：localStorage 读写、状态转换、边界条件无数据丢失或污染
3. **跨页面一致性**：学生端与家长看板的数据口径一致
4. **兼容性**：主流浏览器 + 主要移动设备视口正常可用
5. **回归防护**：每次代码变更后，核心流程可自动验证

---

## 2. 测试策略

采用 **自动化为主、手动为辅** 的混合策略：

| 类型 | 覆盖范围 | 执行频率 | 工具 |
|------|----------|----------|------|
| E2E 自动化 | 功能逻辑、数据持久化、跨页面一致性 | 每次 commit / PR | Playwright |
| 模拟验证 | 长周期学习场景（多天/多题）的数据演化 | 重大逻辑变更后 | Node.js 模拟脚本 |
| 手动测试 | 视觉效果、触控交互、微信浏览器 | 版本发布前 | 人工 |
| 部署验证 | 线上环境功能可用性 | 每次部署后 | Playwright + 截图比对 |

## 8. 待明确的测试策略问题

以下问题需要与用户讨论确认：

### Q1：测试的最终目的是什么？

- **选项 A**：发布前一次性验收（当前状态已满足）
- **选项 B**：建立持续集成门禁（需接入 GitHub Actions，每次 push 自动跑测试）
- **选项 C**：长期质量监控（定期跑全量测试 + 生成趋势报告）

### Q2：跨设备数据方案是否立即实施？

- 如果不实施：当前测试已覆盖全部功能，可以收尾
- 如果实施方案2：需要新增云端 API 测试、uid 参数测试、网络异常容错测试

### Q3：是否需要性能基准测试？

- 首屏加载时间、答题切换延迟、大数据量（1000+ 题历史）下的渲染性能

### Q4：兼容性测试深度

- 是否需要真机测试（iPhone/Android 实体设备）？
- 微信内置浏览器是否作为 P0 必过项？
